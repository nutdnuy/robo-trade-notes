# Execution และ Paper Trading

backtest สมมติว่าคำสั่งทุกคำสั่งถึงตลาด ได้ราคาตามที่คิด และได้ครบทุกหุ้น โปรแกรมที่ส่งคำสั่งจริงต้องรับมือกับสิ่งที่ backtest ไม่มี คำสั่งถูกปฏิเสธ ได้หุ้นไม่ครบ เครือข่ายหลุดกลางคัน และโปรแกรมทำงานผิดตอนตีสามขณะที่เราหลับอยู่

บทนี้สร้างชั้นระหว่างกฎซื้อขายกับ broker ด้วย mock broker ที่เราเขียนเอง หลังจบบท ผู้เรียนจะเขียน risk gate ที่ตรวจคำสั่งก่อนส่ง ใช้ client order id กันคำสั่งซ้ำ อ่านสถานะคำสั่งแบบ partial fill วัด implementation shortfall และกระทบยอด position จาก audit log ทุกอย่างทำงานออฟไลน์ ไม่ต่อบัญชีใด

## จาก Backtest สู่คำสั่ง {#backtest-to-orders}

backtest คืนน้ำหนักเป้าหมาย ระบบส่งคำสั่งต้องแปลงน้ำหนักนั้นเป็นคำสั่งที่ส่งได้ทีละขั้น

1. **อ่าน position ปัจจุบันจาก broker** อย่าใช้ค่าที่โปรแกรมจำไว้เอง
2. **คำนวณจำนวนหุ้นที่ต้องซื้อขาย** จากน้ำหนักเป้าหมาย ราคาไม่ปรับล่าสุด และเงินในบัญชี ตาม[บทที่ 8](#/chapter-21)
3. **ผ่าน risk gate** ทุกคำสั่งต้องผ่านการตรวจที่เขียนไว้ก่อน ไม่มีข้อยกเว้น
4. **ส่งคำสั่งพร้อม client order id ที่สร้างจากข้อมูลของคำสั่งนั้น**
5. **ติดตามสถานะ** จนกว่าคำสั่งจะจบ: filled, partially filled, canceled หรือ rejected
6. **กระทบยอด** position จาก log กับ position จาก broker ต้องตรงกัน ถ้าไม่ตรง ให้หยุดแล้วหาสาเหตุ

## Risk gate {#risk-gate}

risk gate คือฟังก์ชันที่ตรวจคำสั่งทุกคำสั่งก่อนถึง broker ถ้าข้อใดไม่ผ่าน คำสั่งถูกปฏิเสธพร้อมเหตุผลที่อ่านได้ ตัวอย่างใน Notebook ตรวจหกข้อ

| ข้อตรวจ | ค่าใน Notebook | ป้องกันอะไร |
| --- | --- | --- |
| Kill switch | ปิดอยู่ | หยุดทุกคำสั่งทันทีเมื่อเปิด |
| Symbol whitelist | DEMO, ALT | AI หรือ bug ส่งคำสั่งหุ้นที่ไม่ได้ตั้งใจ |
| จำนวนเต็มบวก | | จำนวนติดลบ หรือเศษหุ้นในบัญชีที่ไม่รองรับ |
| มูลค่าต่อคำสั่ง | ไม่เกิน 5,000 USD | ทศนิยมผิดตำแหน่ง เช่น 500 หุ้นแทน 50 หุ้น |
| มูลค่า position | ไม่เกิน 8,000 USD ต่อหุ้น | สะสม position จนเกินงบความเสี่ยง |
| จำนวนคำสั่งต่อวัน | ไม่เกิน 6 | loop ที่ส่งคำสั่งไม่หยุด |

ผลจากห้าคำสั่งแรก สองคำสั่งผ่าน สามคำสั่งถูกปฏิเสธ คือหุ้นที่ไม่อยู่ใน whitelist คำสั่ง 500 หุ้นมูลค่าเกือบ 25,000 USD และคำสั่ง 2.5 หุ้น

ค่าในตารางเป็นตัวอย่างสำหรับบัญชีจำลองขนาดเล็ก ให้ตั้งค่าจากงบความเสี่ยงของตัวเอง และเขียนไว้ใน Research Dossier ของบทที่ 12 Local MCP ของ Webull มีตัวเลือกคล้ายกัน เช่น `WEBULL_MAX_ORDER_NOTIONAL_USD` และ `WEBULL_SYMBOL_WHITELIST` แต่คอร์สนี้ไม่ใช้ MCP ส่งคำสั่ง ตาม[Prework P3](#/chapter-17)

## Client order id กันคำสั่งซ้ำ {#idempotency}

ถ้าเครือข่ายหลุดหลังส่งคำสั่ง โปรแกรมไม่รู้ว่าคำสั่งถึง broker แล้วหรือยัง ถ้าส่งใหม่ด้วยคำสั่งที่ไม่มีเลขอ้างอิง เราอาจซื้อสองเท่า

วิธีแก้คือสร้าง client order id จากข้อมูลที่ไม่เปลี่ยนของคำสั่งนั้น เช่น `d0-DEMO-buy` คือวันที่ตัดสินใจ หุ้น และทิศ ส่งซ้ำกี่ครั้ง id ก็เหมือนเดิม broker ที่รองรับ id นี้จะคืนคำสั่งเดิมแทนการสร้างใหม่ ใน Notebook การส่ง `d0-DEMO-buy` ครั้งที่สองบันทึกเป็น `DUPLICATE_IGNORED` และมีคำสั่งนี้เพียงหนึ่งคำสั่ง

อย่าสร้าง id จากเวลาปัจจุบันหรือเลขสุ่ม เพราะการส่งซ้ำจะได้ id ใหม่ทุกครั้ง ให้ตรวจเอกสารของ broker ว่าใช้ id ซ้ำได้นานแค่ไหน และมีกติกาเรื่องความยาวหรือตัวอักษรอย่างไร

## Fill ที่ open วันถัดไป และ partial fill {#fills}

`MockBroker` ทำตามกติกาเวลาของคอร์ส สัญญาณจาก close วัน 0 ส่งคำสั่งได้หลังตลาดปิด และ fill ที่ open วัน 1 บวก slippage 5 bps นอกจากนี้ยังจำกัดว่าคำสั่งหนึ่งได้หุ้นไม่เกิน 1% ของ volume ของแท่งนั้น ส่วนที่เหลือยกเลิกเมื่อจบวัน

| คำสั่ง | ขอ | ได้ | สถานะ |
| --- | --- | --- | --- |
| DEMO ซื้อ | 80 | 80 | FILLED |
| ALT ซื้อ | 40 | 31 | PARTIALLY_FILLED_THEN_CANCELED |

ALT เป็นหุ้นสมมติที่ซื้อขายวันละราว 3,000 หุ้น 1% ของ volume วัน 1 คือ 31 หุ้น คำสั่ง 40 หุ้นจึงได้ไม่ครบ backtest ที่สมมติว่าได้ครบทุกครั้งจะประเมินผลของหุ้นสภาพคล่องต่ำผิด หลังจาก partial fill โปรแกรมต้องตัดสินใจว่าจะส่งส่วนที่เหลือในวันถัดไป หรือปรับน้ำหนักเป้าหมายแทน กติกานี้ต้องเขียนไว้ก่อน

## Implementation shortfall {#shortfall}

implementation shortfall วัดว่าราคาที่ได้จริงห่างจากราคาตอนตัดสินใจเท่าไร เราแยกเป็นสองส่วน

$$
\text{shortfall} \approx \underbrace{\frac{O_{t+1}}{C_t} - 1}_{\text{gap ข้ามคืน}} \;+\; \underbrace{\text{slippage}}_{\text{ราคาที่ได้เทียบกับ open}}
$$

ค่าบวกแปลว่าซื้อแพงกว่าราคาตอนตัดสินใจ

| หุ้น | ราคาตอนตัดสินใจ (close วัน 0) | open วัน 1 | ราคาที่ได้ | shortfall | gap | slippage |
| --- | --- | --- | --- | --- | --- | --- |
| DEMO | 49.43 | 49.21 | 49.2346 | −39.5 bps | −44.5 bps | +5.0 bps |
| ALT | 119.53 | 119.73 | 119.7899 | +21.7 bps | +16.7 bps | +5.0 bps |

gap ข้ามคืนเป็นส่วนที่ใหญ่กว่า และมีทั้งบวกและลบ ในระยะยาว gap ไม่ได้เข้าข้างเรา แต่ถ้ากฎของเราซื้อหุ้นที่เพิ่งขึ้นแรง gap มักไม่เข้าข้าง เพราะคนอื่นเห็นสัญญาณเดียวกัน ให้เก็บ shortfall ของทุกคำสั่งไว้เทียบกับต้นทุนที่สมมติใน backtest ถ้าค่าเฉลี่ยจริงสูงกว่า ให้แก้ต้นทุนใน backtest แล้วรันใหม่

## Limit order และ kill switch {#limit-and-kill}

limit order กำหนดราคาสูงสุดที่ยอมซื้อ ใน Notebook คำสั่งซื้อ DEMO ที่ limit 46.99 ถูกยกเลิก เพราะ open วัน 2 อยู่ที่ 48.18 limit order ลด slippage แต่เพิ่มความเสี่ยงที่จะไม่ได้หุ้นเลย ถ้ากฎต้องการถือหุ้นตามสัญญาณ backtest ต้องนับวันที่คำสั่งไม่ได้ fill ด้วย

kill switch คือสวิตช์เดียวที่หยุดทุกคำสั่ง ต้องเปิดได้ง่ายโดยไม่ต้องแก้โค้ด เช่น ไฟล์ที่ระบบตรวจก่อนส่งทุกคำสั่ง หรือ environment variable เมื่อเปิดแล้ว Notebook ปฏิเสธคำสั่งขาย DEMO ทันทีพร้อมเหตุผล `kill switch is on`

## Audit log และการกระทบยอด {#audit-log}

ทุกเหตุการณ์ของคำสั่งถูกบันทึกเป็นหนึ่งบรรทัด ได้แก่ สร้าง ปฏิเสธ ส่งซ้ำ fill และยกเลิก log นี้ต้องพอสร้าง position ทั้งหมดใหม่ได้โดยไม่ต้องถาม broker

```json
{"event": "NEW", "day": 0, "client_order_id": "d0-DEMO-buy", "symbol": "DEMO", "side": "BUY", "qty": 80, "type": "MARKET"}
```

ก่อนส่งคำสั่งรอบถัดไป ระบบกระทบยอด position ที่รวมจาก log กับ position ที่ broker รายงาน ใน Notebook ทั้งสองได้ DEMO 80 หุ้น และ ALT 31 หุ้นตรงกัน ถ้าไม่ตรง ให้เปิด kill switch แล้วหาสาเหตุก่อน อย่าให้โปรแกรมแก้ position เองโดยอัตโนมัติ

## Paper trading ทดสอบอะไรได้ และอะไรไม่ได้ {#paper-trading}

หลังระบบผ่าน mock broker แล้ว ขั้นต่อไปคือบัญชี paper trading ของ broker เอกสาร Webull ฝั่งสหรัฐระบุว่า key ของ paperTrade สร้างในสภาพแวดล้อม paperTrade คำสั่งเป็นการจำลอง ยอดเงินและ position แยกจากบัญชีจริง และข้อมูลตลาดอาจล่าช้าหรือเป็นข้อมูลสังเคราะห์ ฝั่ง Local MCP มีสภาพแวดล้อม `uat` เป็น sandbox

| Paper trading ทดสอบได้ | Paper trading ทดสอบไม่ได้ |
| --- | --- |
| การยืนยันตัวตนและการจัดการ token | slippage และ market impact จริง |
| รูปแบบคำสั่งและข้อความ error ของ broker | partial fill ที่เกิดจากคนอื่นในตลาด |
| การส่งซ้ำด้วย client order id | ผลตอบแทนของกลยุทธ์ |
| risk gate, kill switch และการกระทบยอด | พฤติกรรมของเราเมื่อเงินจริงขาดทุน |

ผล paper trading จึงไม่ได้ยืนยันว่ากลยุทธ์ได้กำไร มันยืนยันว่าระบบส่งคำสั่งทำงานตามที่ออกแบบ

**ขอบเขตของคอร์ส** การต่อบัญชี paper trading ของผู้เรียนเป็นขั้นที่ผู้เรียนเลือกทำเอง ด้วย key ของตัวเอง หลังผ่านแบบฝึกหัดของบทนี้ครบ คอร์สนี้ไม่ส่งคำสั่งเข้าบัญชีที่มีเงินจริง และไม่เปิดระบบซื้อขายอัตโนมัติ ถ้าจะต่อ paper trading ให้เริ่มจากโหมด dry-run ที่พิมพ์คำสั่งออกมาโดยไม่ส่ง ใช้ key ที่มีสิทธิ์น้อยที่สุด ตั้ง limit และ kill switch ก่อน แล้วเก็บ audit log ทุกคำสั่ง
