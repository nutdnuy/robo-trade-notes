# เชื่อมกลยุทธ์กับโบรกเกอร์ โดยรู้ว่าคำสั่งอยู่ที่ไหน

หลังคำนวณสถานะเป้าหมายได้ งานถัดไปคือทำให้บัญชีขยับเข้าหาเป้าหมายอย่างตรวจสอบได้ ปัญหาสำคัญไม่ได้มีเพียง “ส่งคำสั่งอย่างไร” แต่รวมถึง “ถ้าส่งแล้วไม่ได้รับคำตอบ เราควรทำอะไร” และ “ถ้าซื้อได้เพียงบางส่วน บัญชีถืออยู่เท่าไร”

บทนี้ใช้ Webull Thailand เป็นบริบทของการอ่านเอกสาร แล้วทดลองวงจรคำสั่งด้วยโบรกเกอร์จำลองในเครื่อง คุณจะเห็นเงินสด หุ้นที่ถือ คำสั่งค้าง และค่าธรรมเนียมเปลี่ยนแยกกันอย่างชัดเจน

## เป้าหมาย: ไม่สร้างคำสั่งซ้ำจากความไม่แน่ใจ {#objectives}

เมื่อจบบท คุณจะวางขอบเขตระหว่างกลยุทธ์กับส่วนเชื่อมต่อโบรกเกอร์ได้ อธิบายสถานะรับคำสั่ง จับคู่บางส่วน จับคู่ครบ และยกเลิก รวมทั้งตรวจความต้องการซื้อเพิ่มโดยนับคำสั่งที่ยังค้างอยู่ด้วย

**พื้นฐานที่ใช้:** สถานะเป้าหมาย การจำลองเหตุการณ์ เงินสด/หุ้น และข้อมูลสตรีม ใช้เวลาประมาณ 60–75 นาที ตัวอย่าง Python ใช้เฉพาะ standard library และไม่ต้องมี API key

หนังสือ Hilpisch บทที่ 8 และ 9 ใช้ Oanda และ FXCM เป็นกรณีศึกษา เรานำแนวคิดการแยกข้อมูล บัญชี และคำสั่งมาจัดโครงสร้างใหม่สำหรับ Webull โดยอ้างรายละเอียดผู้ให้บริการจากเอกสาร Webull Thailand [แหล่งอ้างอิง](#references) ชื่อคลาส `PaperBroker` ในบทนี้คือระบบจำลองที่เขียนเอง ไม่ใช่ SDK ของ Webull

## แผนที่เอกสาร: อะไรต้องตรวจแยกกัน {#api-map}

เอกสารทางการแยกบริการข้อมูลตลาดออกจากบริการจัดการบัญชีและคำสั่งซื้อขาย การอ่าน endpoint ได้จึงยังไม่ใช่หลักฐานว่าบัญชีของเรามีสิทธิ์ใช้งานครบทุกส่วน

| สิ่งที่ระบบต้องรู้/ทำ | หมวดเอกสาร Webull ที่เกี่ยวข้อง | สิ่งที่ทดลองในบทนี้ |
| --- | --- | --- |
| รับราคาย้อนหลังและข้อมูลต่อเนื่อง | Market Data, Historical Bars, Streaming | ใช้ราคาและเหตุการณ์ที่สร้างเอง |
| ตรวจเงินและหุ้นที่ถือ | Assets: Balance และ Positions | ตารางสถานะใน `PaperBroker` |
| ตรวจคำสั่งที่ยังไม่จบ | Order Query | ค้นคำสั่งจาก ID ภายในเครื่อง |
| รับการเปลี่ยนสถานะคำสั่ง/สถานะถือครอง | Trade Events | เรียกเหตุการณ์จำลองทีละรายการ |
| ขอซื้อ แก้ไข หรือยกเลิก | Trading | เปลี่ยนสถานะของวัตถุในหน่วยความจำ |

แผนที่นี้ตรวจจาก [Trading API](https://developer.webull.co.th/apis/docs/reference/custom/trading-api/), [Assets](https://developer.webull.co.th/apis/docs/reference/trade-api/assets/), [Order Query](https://developer.webull.co.th/apis/docs/reference/trade-api/order-query/) และ [Trade Events](https://developer.webull.co.th/apis/docs/reference/custom/trading-events/) วันที่ 11 กันยายน 2026

หากจะต่อบัญชีในขั้นถัดไป ต้องยืนยันประเทศ/นิติบุคคลผู้ให้บริการ ประเภทบัญชี สิทธิ์ OpenAPI และข้อมูลตลาด สภาพแวดล้อมที่ได้รับอนุญาต รวมถึง SDK และข้อจำกัดคำสั่งของบัญชีนั้น บทนี้ยังไม่ได้ตรวจสิทธิ์เฉพาะบัญชีของ Nuth จึงจบการทดลองที่โบรกเกอร์จำลองในเครื่อง

UAT ที่กล่าวถึงในคู่มือ SDK เป็นสภาพแวดล้อมทดสอบของผู้ให้บริการ ส่วนคำว่า **paper simulation** ในบทนี้หมายถึงระบบจำลองของหลักสูตร ไม่ได้ยืนยันว่าบัญชี Webull ใดมี paper-trading API ให้ใช้

## สร้างสัญญาภายในให้กลยุทธ์พึ่งพาน้อยที่สุด {#adapter-contract}

กลยุทธ์ควรตอบว่าอยากถือเท่าไร ส่วน **broker adapter** ทำหน้าที่แปลงความต้องการและเหตุการณ์ให้เข้ากับผู้ให้บริการ เราจึงแยก 3 ข้อความ:

- **Target:** อยากถือ `DEMO` 10 หุ้น เป็นผลจากกติกาและการกำหนดขนาด
- **Intent:** ความตั้งใจซื้อเพิ่ม 10 หุ้น ภายใต้กติกาและเวลาตัดสินใจหนึ่งครั้ง มี ID คงที่
- **Order / Fill:** คำสั่งที่ได้รับการยืนยัน และจำนวนที่จับคู่แล้ว เป็นหลักฐานการเปลี่ยนบัญชี

```python
# These are the course mock's methods, not Webull SDK calls.
broker.submit(intent_id, "DEMO", 10, "100.00")
broker.query(intent_id)
broker.apply_fill(intent_id, "fill-1", 4, "99.90", "0.40")
```

`submit`, `query` และ `apply_fill` เป็นชื่อที่เราออกแบบเองเพื่อสอนสัญญาภายใน ห้ามเปลี่ยนเพียง hostname แล้วใช้เป็น Webull client การทำ adapter จริงต้องจับคู่ request/response และสถานะจาก SDK รุ่นที่ตรวจแล้ว รวมถึงกรณี error

ตัวอย่างใช้ `Decimal` เพื่อคำนวณจำนวนเงินจากเลขฐานสิบที่กำหนด แยก field ราคากับจำนวนหุ้น และไม่ใส่ API key ใน Notebook เว็บไซต์ไม่รับข้อมูลบัญชีหรือ App Secret

## เมื่อคำสั่งมีชีวิตของตัวเอง {#order-lifecycle}

**Acknowledgement** คือการยืนยันว่าได้รับคำสั่ง ส่วน **fill** คือเหตุการณ์จับคู่ที่ทำให้เงินสดและจำนวนหุ้นเปลี่ยน คำสั่งที่ได้รับการยอมรับอาจยังไม่ซื้อได้เลย หรืออาจซื้อได้เพียงบางส่วน

| สถานะภายในตัวอย่าง | ความหมาย | เปลี่ยนจำนวนหุ้นหรือยัง |
| --- | --- | --- |
| ACCEPTED | mock รับคำสั่งแล้ว | ยัง |
| PARTIAL | ซื้อได้บางส่วน | เพิ่มเฉพาะส่วนที่ fill |
| FILLED | ซื้อครบจำนวนคำสั่ง | เพิ่มครบตาม fill ที่ได้รับ |
| CANCELED | หยุดส่วนที่ยังไม่ fill | ส่วนที่ซื้อแล้วคงอยู่ |

ระบบจริงอาจมีสถานะและ transition มากกว่านี้ เช่น pending, rejected หรือ expired รวมถึงเหตุการณ์ที่มาถึงหลังคำขอยกเลิก สถานะในตารางเป็น vocabulary ของตัวอย่าง ไม่ใช่การรับรองรหัสสถานะ Webull

การกด “ยกเลิก” เป็นคำขออีกครั้งหนึ่ง จึงต้องแยก **ขอยกเลิก** ออกจาก **ยืนยันยกเลิกสำเร็จ** mock ในบทนี้ยืนยันยกเลิกทันทีเพื่อให้เห็นบัญชีได้ง่าย และไม่จำลองการแข่งขันระหว่าง cancel กับ fill ที่อยู่ระหว่างทาง ประเด็นนี้ต้องเพิ่มในงานทดสอบ adapter จริง

## ทดลอง: คำตอบหาย หลังโบรกเกอร์รับคำสั่ง {#timeout-example}

เริ่มต้นด้วยเงินสด 2,000 USD สมมติ ถือหุ้น 0 หุ้น ตั้งเป้าถือ 10 หุ้น และสร้างคำสั่งซื้อแบบ limit ที่ราคาไม่เกิน 100 USD ต่อหุ้น ไม่ใช้ leverage หรือการขายชอร์ต ค่าธรรมเนียมกำหนดเองที่ 0.10 USD ต่อหุ้น เพื่อให้เห็นผลต่อบัญชี ไม่มี spread หรือ impact model; ราคาจับคู่กำหนดเป็นเหตุการณ์ตัวอย่าง

ใช้ ID เดิมผูกกับการตัดสินใจหนึ่งครั้ง แล้วจำลองว่าระบบรับคำสั่งสำเร็จแต่คำตอบกลับมาไม่ถึง:

```python
key = "DEMO|2026-01-05T14:31:00Z|v1|BUY10"
try:
    broker.submit(key, "DEMO", 10, "100.00", lose_response=True)
except TimeoutError:
    recovered = broker.query(key)
    assert recovered is not None
```

เมื่อ timeout เรารู้เพียงว่าไม่ได้รับผลลัพธ์ ไม่รู้แน่ว่าคำสั่งล้มเหลว การสร้าง ID ใหม่แล้วซื้ออีกทันทีอาจทำให้มีคำสั่งสองชุด ใน mock นี้จึงตรวจจาก ID เดิมและพบ `ACCEPTED` โดยไม่เพิ่มคำสั่ง

**Idempotency** คือการทำซ้ำโดยไม่เพิ่มผลลัพธ์อีกชุด ในตัวอย่างการส่ง intent เดิมซ้ำจะคืนคำสั่งเดิม และถ้าใช้ ID เดิมแต่เปลี่ยนจำนวนหรือราคา จะเกิดข้อผิดพลาด คุณสมบัตินี้เป็นสัญญาของ mock เท่านั้น การมี `client_order_id` ใน API จริงยังไม่เพียงพอที่จะอนุมานว่าการส่งซ้ำรับประกันพฤติกรรมเดียวกันทุกกรณี

หากตรวจ API แล้วไม่พบคำสั่งหลัง timeout อาจเป็นความล่าช้าในการแสดงผลหรือคำสั่งไม่ได้รับจริง ต้องเก็บสถานะ “ยังไม่ทราบผล” จำกัดการลองใหม่ และใช้กติกา reconcile ที่ตรวจตามผู้ให้บริการ ห้ามสรุปว่าปลอดภัยที่จะสร้างคำสั่งใหม่จากการค้นครั้งเดียว

## ทดลองต่อ: ซื้อได้ 4 หุ้น แล้วอีก 6 หุ้น {#partial-fills}

รันไฟล์หรือ Notebook แล้วอ่านผลทีละจุด:

```shell
python lesson_09.py
```

fill แรกซื้อ 4 หุ้นที่ 99.90 USD ค่าธรรมเนียม 0.40 USD เงินที่จ่ายคือ `4 × 99.90 + 0.40 = 400.00` เหลือเงินสด 1,600 USD ถือ 4 หุ้น และค้างซื้ออีก 6 หุ้น

สูตรหาจำนวนที่ยังจำเป็นต้องส่งเพิ่มในกรณีซื้อฝั่งเดียวคือ:

$$q_{new}=q_{target}-q_{held}-q_{pending\ buy}$$

ดังนั้น `10 − 4 − 6 = 0` ไม่ใช่ 6 การลบเฉพาะหุ้นที่ถือจะสร้างคำสั่งเกินเป้าหมาย เพราะมองข้ามคำสั่งเดิมที่ยังมีโอกาส fill

| จุดตรวจ | ถือหุ้น | ค้างซื้อ | เงินสด USD | ค่าธรรมเนียมสะสม USD |
| --- | ---: | ---: | ---: | ---: |
| ก่อนส่งคำสั่ง | 0 | 0 | 2,000.00 | 0.00 |
| รับคำสั่งแล้ว | 0 | 10 | 2,000.00 | 0.00 |
| fill แรก 4 หุ้น | 4 | 6 | 1,600.00 | 0.40 |
| รับ fill แรกซ้ำ | 4 | 6 | 1,600.00 | 0.40 |
| fill ที่สอง 6 หุ้น | 10 | 0 | 999.40 | 1.00 |

fill ที่สองมีราคา 100.00 USD ค่าธรรมเนียม 0.60 USD จึงจ่ายอีก 600.60 USD ราคาซื้อเฉลี่ย **ก่อนค่าธรรมเนียม** คือ:

$$\bar P=\frac{4(99.90)+6(100.00)}{10}=99.96$$

หากประเมินหุ้นที่ราคา 100 USD มูลค่าบัญชีคือ `999.40 + 10 × 100 = 1,999.40 USD` ตัวเลขนี้เป็นการกระทบยอดบัญชีตามเหตุการณ์ที่กำหนด ไม่ใช่ผลทดสอบความสามารถทำกำไรของกลยุทธ์

โปรแกรมตรวจ ID ของ fill เพื่อไม่หักเงินซ้ำ และตรวจว่าข้อมูลของ ID เดิมเหมือนเดิม หากจำนวนหรือราคาเปลี่ยนต้องตรวจสอบ ไม่ถือเป็น duplicate ที่ลบทิ้งได้ตามปกติ

## ข้อจำกัดที่ต้องรู้ก่อนเปลี่ยน mock เป็น adapter {#integration-boundary}

ตัวอย่างนี้มีหุ้นเดียว คำสั่งซื้ออย่างเดียว และจำนวนหุ้นเป็นจำนวนเต็ม ไม่มี margin, settlement, currency conversion, lot size, corporate actions หรือภาษี การสำรองเงินสำหรับคำสั่งค้างใช้จำนวนที่เหลือคูณ limit; ยังไม่ได้สำรองค่าธรรมเนียมล่วงหน้าครบทุกคำสั่ง จึงต้องเผื่อค่าธรรมเนียมเพิ่มเติมก่อนประยุกต์กับระบบอื่น

การเก็บ ID อยู่ในหน่วยความจำ เมื่อโปรแกรมดับข้อมูลนี้หายไป บทถัดไปจะเพิ่ม journal และการกู้สถานะ การย้ายโค้ดนี้ขึ้นเซิร์ฟเวอร์โดยไม่เพิ่ม state persistence ยังไม่แก้ปัญหาคำสั่งซ้ำหลัง restart

ในเอกสารปัจจุบันมี [List Open Orders](https://developer.webull.co.th/apis/docs/reference/trade-api/order-query/) และ [List Account Positions](https://developer.webull.co.th/apis/docs/reference/trade-api/account-position/) ซึ่งเป็นส่วนของหลักฐานที่จะใช้ตรวจสถานะจริง แต่การเขียน adapter ต้องตรวจ pagination, เขตเวลา, status mapping และความสอดคล้องของ snapshot ให้ครบ ไม่ใช่อ่านจำนวนหุ้นอย่างเดียว

การตรวจ SDK 3.0.0 สำหรับหลักสูตรยืนยันว่ามีโมดูล request หลายรุ่นแยกกัน จึงไม่ควรหยิบตัวอย่างต่างรุ่นมารวมจากชื่อฟังก์ชันที่คล้ายกัน บทนี้ไม่ได้เรียก SDK และไม่ได้ส่งคำสั่งแม้แต่ใน UAT ผลที่เห็นทั้งหมดมาจาก mock

## แบบฝึกหัด: ยกเลิกส่วนที่เหลือ {#exercise}

สร้างคำสั่งซื้อ 10 หุ้นที่ 100 USD ให้ fill 4 หุ้นที่ 100 USD เสียค่าธรรมเนียม 0.40 USD แล้วเรียก `cancel` ใน mock ถ้ายังต้องการถือ 10 หุ้น การตัดสินใจรอบใหม่ควรขออีกกี่หุ้น และเหลือเงินเท่าไร?

**แนวเฉลย:** หลังยืนยันยกเลิก ส่วนค้างซื้อเป็น 0 แต่หุ้นที่ซื้อแล้วคงเป็น 4 จึงยังต้องการอีก `10 − 4 − 0 = 6` หุ้น เงินสดเหลือ `2,000 − 400 − 0.40 = 1,599.60 USD` คำสั่งใหม่ต้องผ่านการตรวจความเสี่ยงและใช้ intent ของการตัดสินใจรอบใหม่ ไม่ใช่แก้ payload ของ ID เดิม

เพิ่มแบบทดสอบอีกสองกรณี: ส่ง intent เดิมซ้ำต้องมีคำสั่งเพียงหนึ่งรายการ และส่ง fill ID เดิมซ้ำต้องไม่เพิ่มหุ้นหรือหักเงินอีก ลองเปลี่ยน payload ของ ID เดิมเพื่อให้เห็นว่าโปรแกรมหยุดตรวจความขัดแย้งอย่างไร

Yves Hilpisch, *Python for Algorithmic Trading*, บทที่ 8 “CFD Trading with Oanda” หน้าในเล่ม 223 และ “The Oanda API” หน้า 229 (PDF หน้า 243, 249); บทที่ 9 “FX Trading with FXCM” หน้า 249 และ “Working with the API” หน้า 256 (PDF หน้า 269, 276) ใช้เป็นกรอบเรื่องการทำงานกับผู้ให้บริการ ไม่ใช้ endpoints หรือโค้ดของโบรกเกอร์เหล่านั้น
2. [Webull Thailand: Trading API](https://developer.webull.co.th/apis/docs/reference/custom/trading-api/), [Order Query](https://developer.webull.co.th/apis/docs/reference/trade-api/order-query/), [Trade Events](https://developer.webull.co.th/apis/docs/reference/custom/trading-events/) และ [Account Positions](https://developer.webull.co.th/apis/docs/reference/trade-api/account-position/) ตรวจวันที่ 11 กันยายน 2026
3. [Official Webull Python SDK](https://github.com/webull-inc/webull-openapi-python-sdk) ตรวจโครงสร้าง request จาก wheel 3.0.0 ที่เก็บไว้เพื่อการตรวจหลักสูตร วันที่ 11 กันยายน 2026 การมีคลาสใน package ไม่ยืนยันสิทธิ์บัญชีหรือ regional support ของแต่ละรุ่น
4. ผลตารางทั้งหมดคำนวณจาก `lesson_09.py` และ Notebook ด้านล่าง ตัวอย่างนี้เป็นโค้ดใหม่ของหลักสูตร
