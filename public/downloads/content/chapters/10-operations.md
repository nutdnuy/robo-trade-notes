# ทำให้ระบบหยุดได้ กู้กลับได้ และตรวจสอบได้

ระบบ Robo Trade ไม่ได้จบเมื่อกลยุทธ์ส่งคำสั่งได้ครั้งแรก งานที่เหลือคือทำให้เราตอบได้ว่าโปรแกรมกำลังเชื่อข้อมูลใด ถือหุ้นจริงเท่าไร และควรหยุดเมื่อใด โดยเฉพาะตอนเครื่องดับหรือเครือข่ายหายกลางทาง

บทสุดท้ายจะเชื่อมสัญญาณ สถานะบัญชี กติกาความเสี่ยง และบันทึกเหตุการณ์เข้าด้วยกันเป็นงานทดลองครบวงจร คุณจะจำลองการล่มหลังซื้อได้บางส่วน แล้วกู้ระบบกลับมาโดยไม่เพิ่มจำนวนหุ้นจากข้อความซ้ำ

## เป้าหมาย: กลับมาทำงานโดยไม่เดาสถานะ {#objectives}

เมื่อจบบท คุณจะสร้างบันทึกเหตุการณ์ที่ replay ได้ กระทบยอดเงินสด หุ้น และคำสั่งค้างก่อนกลับมาทำงาน อธิบายเหตุผลที่ระบบบล็อกคำสั่งใหม่ และออกแบบการเฝ้าดูระบบพร้อมขั้นตอนกู้คืนที่คนอื่นทำตามได้

**พื้นฐานที่ใช้:** บทข้อมูลสตรีมและวงจรคำสั่ง โดยเฉพาะ partial fill, timeout และ pending quantity ใช้เวลาประมาณ 75–90 นาที รวม capstone ใน Notebook

หนังสือ Hilpisch บทที่ 10 เชื่อมเรื่องการจัดการเงินทุน อัลกอริทึมออนไลน์ โครงสร้างพื้นฐาน และการบันทึก/เฝ้าดูระบบ ส่วน journal replay, reconciliation และ risk gate ด้านล่างเป็นแบบฝึกหัดใหม่ที่เพิ่มเพื่อทำให้ข้อผิดพลาดจากการทำงานจริงสังเกตได้ [แหล่งอ้างอิง](#references)

## แยกสถานะกลยุทธ์ออกจากข้อเท็จจริงของบัญชี {#state-model}

การบันทึกเพียง `position = 1` ไม่พอสำหรับกู้ระบบ เพราะ 1 อาจหมายถึง “สัญญาณอยาก Long” หรือ “เชื่อว่าซื้อแล้ว” เราต้องแยกความตั้งใจออกจากหลักฐานการจับคู่

| สถานะที่ต้องเก็บ | ตัวอย่าง | ใช้ตอนกู้ระบบ |
| --- | --- | --- |
| รุ่นของกติกาและพารามิเตอร์ | SMA 3, version v1 | รู้ว่าสัญญาณเกิดจากอะไร |
| ข้อมูลล่าสุดที่ใช้ | bar end และ available time | ตรวจว่า warm-up/ข้อมูลยังต่อเนื่อง |
| Intent ที่บันทึกก่อนส่ง | อยากซื้อเพิ่ม 10 หุ้น | ค้นคำสั่งที่อาจรับแล้วแต่คำตอบหาย |
| ACK และคำสั่งค้าง | รับแล้ว เหลือซื้อ 6 หุ้น | ป้องกันส่งซ้ำจากการนับไม่ครบ |
| Fill ที่ยืนยันแล้ว | 4 หุ้น × 99.90 + fee 0.40 | คำนวณเงินจริงและจำนวนหุ้น |
| สถานะควบคุม | paused, reconciled, stopped | ตัดสินใจว่าจะอนุญาตงานใหม่หรือไม่ |

**Journal** คือบันทึกเหตุการณ์เรียงลำดับที่เก็บรายละเอียดพอให้สร้างสถานะขึ้นใหม่ การบันทึก intent ก่อนเรียกบริการเป็นจุดเริ่มต้นของการจัดการกรณีล่มระหว่างทาง แต่ยังไม่ทำให้เกิดธุรกรรมเดียวกันแบบอะตอมระหว่างเครื่องเรากับโบรกเกอร์ เมื่อเริ่มใหม่จึงต้องตรวจผลกับต้นทางเสมอ

ตัวอย่างใช้ `event_id` คงที่ และให้ ID เดิมพร้อมข้อมูลเดิมไม่มีผลซ้ำ หากพบ ID เดิมแต่ข้อมูลต่างกัน จะหยุดตรวจความขัดแย้ง การทำ adapter จริงต้องรักษา execution ID เดียวกันทั้งเส้นทาง event stream และประวัติที่ดึงตอน recovery เพื่อให้การตรวจซ้ำทำงานได้

## ทดลอง: เครื่องดับหลังซื้อได้ 4 หุ้น {#recovery-example}

ใช้บัญชีและ fill จำลองแบบเดียวกับบทก่อน เริ่มเงิน 2,000 USD หุ้น 0 หุ้น สมมติ journal ในเครื่องบันทึกได้ถึง fill แรก: ซื้อ 4 หุ้นที่ 99.90 USD ค่าธรรมเนียม 0.40 USD จากนั้นเครื่องล่ม ขณะเดียวกันฝั่งโบรกเกอร์จำลองซื้ออีก 6 หุ้นที่ 100 USD ค่าธรรมเนียม 0.60 USD จนครบ

เมื่อเริ่มโปรแกรมใหม่ เราได้สองชุดข้อมูล:

- journal เดิม: intent, ACK และ fill แรก
- ประวัติจาก mock broker: fill แรกและ fill ที่สอง

```python
before = replay(JOURNAL)
after = replay(JOURNAL + BROKER_FILLS)
```

ผลที่รันได้จริง:

| วิธีสร้างสถานะ | หุ้น | เงินสด USD | ข้อสรุป |
| --- | ---: | ---: | --- |
| อ่าน journal เดิมอย่างเดียว | 4 | 1,600.00 | ยังขาด fill ที่เกิดขณะเครื่องล่ม |
| replay รวมข้อมูลที่กู้มา และตรวจ ID ซ้ำ | 10 | 999.40 | ตรงกับ snapshot จำลอง |
| replay ประวัติเดิมซ้ำอีกหลายครั้ง | 10 | 999.40 | ไม่เพิ่มหุ้นหรือหักเงินซ้ำ |

fill แรกมีอยู่ทั้งสองชุด แต่ถูกนับครั้งเดียว ด้วยเหตุนี้จึงไม่ควรบวกยอดซื้อสะสมจากทุกข้อความที่รับโดยตรง หากผู้ให้บริการส่ง cumulative filled quantity ต้องคำนวณส่วนที่เพิ่มจากยอดที่เคยรับอย่างมีหลักฐาน แทนการตีความยอดสะสมเป็น fill ใหม่

Notebook มีตัวอย่างเขียน journal ลงไฟล์ชั่วคราวแล้วอ่านกลับ เพื่อแยกการกู้สถานะออกจากตัวแปรที่ค้างใน kernel ข้อมูลเงินใช้ `Decimal` จากข้อความฐานสิบเพื่อรักษาตัวเลขในแบบฝึกหัด

## Reconciliation ก่อนกลับมาเดินต่อ {#reconciliation}

**Reconciliation** คือการกระทบยอดระหว่างสิ่งที่ระบบคำนวณไว้กับข้อมูลอ้างอิงจากบัญชี ไม่ใช่การบังคับให้บัญชีจริงเปลี่ยนตามตัวแปรในเครื่อง

ในตัวอย่างตรวจว่าถือ 10 หุ้น เงินสด 999.40 USD ไม่มีคำสั่งค้าง และไม่มี intent ที่ยังไม่ทราบผลครบทุกเงื่อนไข จึงตั้ง `reconciled = True` ถ้าตรวจจำนวนหุ้นตรงแต่คำสั่งซื้ออีกชุดยังเปิดอยู่ ระบบอาจซื้อเกินเป้าหมายหลังเดินต่อได้

ลำดับกู้คืนที่ควรเขียนเป็นขั้นตอนปฏิบัติได้คือ:

1. เริ่มในสถานะพักการสร้างคำสั่งใหม่ โหลดรุ่นกติกาและ journal
2. ตรวจ intent ที่ยังไม่ทราบผลกับประวัติคำสั่งและคำสั่งเปิด
3. รับ fills/การแก้รายการที่ขาด แปลงเข้าสู่รูปแบบกลาง และตรวจซ้ำ
4. เปรียบเทียบหุ้น เงินสด และคำสั่งค้าง รวมความต่างจาก manual trade หรือ corporate action
5. เติมข้อมูลช่วงที่ขาดเพื่อเตรียมสัญญาณ โดยไม่ส่งคำสั่งย้อนเวลา
6. ปลดสถานะพักเมื่ออธิบายความต่างได้ครบ และผ่านเงื่อนไขการกลับมาทำงานที่กำหนดไว้

Webull แยกบริการ [Assets](https://developer.webull.co.th/apis/docs/reference/trade-api/assets/) กับ [Order Query](https://developer.webull.co.th/apis/docs/reference/trade-api/order-query/) จึงควรตรวจทั้งสองมุม การดึงข้อมูลหลายหน้าและหลายคำขออาจไม่ได้เป็น snapshot ณ เวลาเดียวกัน ต้องตรวจ timestamp/ความสอดคล้องตามบริการและหลีกเลี่ยงการเทียบยอดที่กำลังเปลี่ยนโดยไม่รู้ตัว

mock นี้สมมติ snapshot พร้อมกันและไม่มีการแก้รายการย้อนหลัง การตรงกันของตัวอย่างจึงพิสูจน์ตรรกะ replay ที่ตั้งไว้ ไม่ได้พิสูจน์ว่า adapter จัดการทุกกรณีของบัญชีจริงแล้ว

## ประตูตรวจความเสี่ยงก่อนคำสั่งทุกครั้ง {#risk-gates}

**Risk gate** คือชุดเงื่อนไขที่ต้องผ่านก่อนส่งความตั้งใจซื้อขายไปยังส่วนดำเนินการ ให้เหตุผลที่ตรวจสอบได้แทนการคืนเพียง “ไม่สำเร็จ”

ตัวเลขต่อไปนี้กำหนดเพื่อฝึกเขียนโปรแกรมเท่านั้น ไม่ใช่ขนาดการลงทุนที่แนะนำ และเป็นนโยบายตัวอย่างสำหรับคำสั่งใหม่ในบทนี้:

| กติกา | ค่าของห้องทดลอง | ป้องกันอะไรในขอบเขตตัวอย่าง |
| --- | ---: | --- |
| จำนวนหุ้นหลัง fill รวมคำสั่งค้าง | ไม่เกิน 20 หุ้น | การเพิ่มสถานะเกินเพดาน |
| มูลค่าคำสั่งใหม่ | ไม่เกิน 500 USD | การส่งขนาดผิดโดยไม่ได้ตั้งใจ |
| อายุข้อมูล | ไม่เกิน 20 วินาที | ตัดสินใจจากราคาที่เก่าเกินกำหนด |
| ผลกำไรขาดทุนรายวัน | หยุดคำสั่งใหม่เมื่อ ≤ −20 USD | ใช้ stop condition ที่กำหนดไว้ |
| เงินพร้อมใช้ | พอหลังหักยอดกันไว้และ fee buffer | การใช้เงินที่คำสั่งอื่นต้องใช้ |
| สถานะบัญชี | กระทบยอดแล้ว ไม่มี intent ค้างไม่ทราบผล | การซื้อเพิ่มบนข้อมูลไม่แน่นอน |
| คำสั่งหยุดโดยผู้ดูแล | ต้องไม่เปิดใช้งาน | ให้มนุษย์หยุดระบบได้ |

เงื่อนไขขนาดต้องนับ worst-case ที่คำสั่งซื้อค้างทั้งหมดได้ fill:

$$q_{held}+q_{pending\ buy}+q_{new}\le q_{max}$$

ผลการทดลองเมื่อถืออยู่ 10 หุ้น เงิน 999.40 USD และจะขอซื้อเพิ่มที่ 100 USD:

| สถานการณ์ | ผลจากโปรแกรม |
| --- | --- |
| ซื้อ 3 หุ้น ข้อมูลอายุ 2 วินาที สถานะตรงกัน | ALLOW_SIMULATION |
| ข้อมูลอายุ 30 วินาที | STALE_DATA |
| ซื้อ 6 หุ้น มูลค่า 600 USD | ORDER_VALUE_LIMIT |
| P&L รายวัน −21 USD | LOSS_LIMIT |
| ยังไม่กระทบยอด | STATE_UNCERTAIN |
| ผู้ดูแลกดหยุด | MANUAL_STOP |

P&L ที่ป้อนในชุดทดสอบเป็นค่าจำลองเพื่อทดสอบแต่ละเงื่อนไข ระบบจริงต้องนิยามวันตาม timezone บัญชี จุดเริ่มวัน ราคาประเมิน และการจัดการฝากถอนให้ชัดเจน รวม realized/unrealized P&L และต้นทุนตามนโยบาย ห้ามให้การ restart รีเซ็ตฐานขาดทุนแล้วเดินต่อเอง

**หยุดคำสั่งใหม่ไม่ได้ปิดสถานะเดิม** คำสั่งค้างอาจยัง fill และหุ้นยังมีความเสี่ยง นโยบาย cancel และการลด/ปิดสถานะฉุกเฉินต้องแยกออกมา พร้อมข้อมูลราคาที่เชื่อถือได้และสิทธิ์ดำเนินการ ตัวอย่างนี้หยุดเพียงการสร้างคำสั่งจำลองใหม่

## Capstone: จากกติกา ถึง fill จำลอง แล้วกู้กลับ {#capstone}

นำชิ้นส่วนมารวมกันโดยใช้ราคาปิดจำลอง 100, 101, 102 USD กติกาคือถ้าราคาปิดล่าสุดสูงกว่า SMA 3 ให้ตั้งเป้าถือ **13 หุ้น** มิฉะนั้นเป้าหมายเป็น 0 ขนาด 13 เป็นค่ากำหนดของห้องทดลอง ไม่ได้มาจากการหาพารามิเตอร์ที่กำไรสูงสุด

ใช้บัญชีที่กู้แล้วจากตัวอย่างก่อน ถือ 10 หุ้น ไม่มีคำสั่งค้าง จึงต้องซื้อเพิ่ม 3 หุ้น หลังคำนวณสัญญาณแล้ว mock กำหนด fill ถัดไปที่ 102 USD และค่าธรรมเนียม 0.30 USD ราคา fill เท่าราคาปิดเพื่อให้อ่านบัญชีง่าย เป็นสมมติฐานจำลอง ไม่ใช่สิทธิ์ที่จะย้อนซื้อที่ราคาปิดที่ใช้สร้างสัญญาณ

```text
ราคาปิด [100, 101, 102] → SMA 3 = 101
สัญญาณ Long → เป้าหมาย 13 หุ้น
หุ้นที่กู้แล้ว 10 → ต้องเพิ่ม 3 หุ้น
ตรวจความเสี่ยง → บันทึก intent → mock ACK → mock fill
บันทึก journal → อ่านกลับ → กระทบยอด
```

ฟังก์ชัน `capstone()` ใน Notebook รันการคำนวณครบทุกขั้น โดยให้เหตุการณ์ ACK และ fill เกิดหลังการตรวจสัญญาณและความเสี่ยง ผลจริงของการรันคือ:

| รายการ | ผล |
| --- | ---: |
| SMA 3 | 101 USD |
| สถานะเป้าหมาย | 13 หุ้น |
| จำนวนซื้อเพิ่มจำลอง | 3 หุ้น |
| เงินจ่ายเพิ่ม รวมค่าธรรมเนียม | 306.30 USD |
| เงินสดหลัง fill | 693.10 USD |
| หุ้นหลัง fill | 13 หุ้น |
| มูลค่าบัญชีเมื่อประเมินที่ 102 USD | 2,019.10 USD |
| สร้างสถานะใหม่จาก journal | PASS |

สมการเงินสดคือ `999.40 − 3 × 102 − 0.30 = 693.10` ส่วนมูลค่าบัญชีคือ `693.10 + 13 × 102 = 2,019.10` ตัวเลขมูลค่ารวมมีไว้ตรวจการบัญชีตามราคาสมมติ ไม่ใช่ผล backtest หรือผลตอบแทนที่คาดหวัง ไม่มีการประเมินความน่าจะเป็นของราคาและการจับคู่ในกรณีนี้

Capstone รองรับเส้นทางซื้อเพิ่มที่เลือกไว้เท่านั้น ถ้าเป้าหมายเป็น 0 ต้องเพิ่มกติกาคำสั่งขาย การสำรองหุ้น และการตรวจ pending sell ให้ครบก่อน โค้ดปัจจุบันจะไม่สร้างคำสั่งขายให้เอง

## ทำให้คนดูแลระบบตอบคำถามได้ {#monitoring}

**Logging** คือการเก็บเหตุการณ์ให้ตรวจย้อนหลังได้ ส่วน **monitoring** คือการดูว่าสถานะปัจจุบันยังอยู่ในเกณฑ์หรือไม่ โปรแกรมอาจยังรัน แต่ใช้ข้อมูลเก่าหรือกำลังส่งคำสั่งที่ถูกปฏิเสธซ้ำ จึงต้องดูมากกว่า CPU และสถานะ process

| สิ่งที่เฝ้าดู | ตัวอย่างข้อมูลที่บันทึก | การตอบสนองที่ออกแบบไว้ |
| --- | --- | --- |
| ความสดและช่องว่างของข้อมูล | last event, last completed bar, gap count | พักสัญญาณและเติมข้อมูล |
| วงจรคำสั่ง | intent ID, status, pending age, reject reason | ตรวจคำสั่งค้างและจำกัด retry |
| สถานะบัญชี | cash, positions, open orders, reconciliation result | พักเมื่ออธิบายความต่างไม่ได้ |
| ความเสี่ยง | exposure รวม pending, day P&L, gate reason | หยุดคำสั่งใหม่ตามเกณฑ์ |
| ระบบพื้นฐาน | disk, queue lag, restart count, clock offset | หยุดอย่างควบคุมได้ก่อนสูญเสียบันทึก |

บันทึก strategy version, config version, data timestamps และเหตุผลตัดสินใจไว้ด้วย เพื่อให้คำถามว่า “ทำไมซื้อครั้งนี้” มีคำตอบจากข้อมูล ณ เวลานั้น ไม่ใช่คำนวณใหม่จากชุดข้อมูลที่แก้ย้อนหลังแล้ว

เก็บ App Secret/Token ในที่ตั้งค่าความลับของเครื่องหรือบริการ แยกจากโค้ดและ log ให้ log อ้างด้วยรหัสที่จำเป็นต่อการติดตาม และจัดสิทธิ์เข้าถึงไฟล์บัญชีตามหน้าที่ Notebook สาธารณะควรมีเฉพาะข้อมูลจำลอง

## ก่อนขึ้นคลาวด์ ต้องซ้อมการล้มเหลว {#cloud-operations}

การย้ายไปคลาวด์ทำให้เลือกโครงสร้างพื้นฐานและเครื่องมือเฝ้าดูได้สะดวกขึ้น แต่ไม่ได้ซ่อมตรรกะการส่งซ้ำหรือบัญชีที่ไม่ตรงกันให้เอง หนังสือใช้ cloud deployment เป็นกรอบการดำเนินงาน ส่วนในหลักสูตรนี้เราจัดข้อกำหนดการทำงานก่อนเลือกผู้ให้บริการ

| ส่วนของระบบ | สิ่งที่ต้องออกแบบ | การซ้อมในระบบทดสอบ |
| --- | --- | --- |
| Environment | Python/package รุ่นแน่นอน, timezone, config แยกสภาพแวดล้อม | สร้างจากเครื่องใหม่แล้ว replay ผลเดิม |
| Process supervision | restart จำกัดครั้ง, เริ่มด้วย paused/reconcile | ปิด process หลังบันทึก intent |
| Storage | เขียนข้อมูลแบบทนต่อการล่ม, backup และ restore | กู้จาก backup และตรวจ event ที่ขาด |
| Network | timeout และ bounded backoff สำหรับงานที่ลองซ้ำได้ | ตัดคำตอบหลัง mock รับคำสั่ง |
| Monitoring | health check และเหตุการณ์ที่ต้องแจ้งผู้ดูแล | ป้อน stale data และผลกระทบยอดไม่ตรง |
| Stop control | หยุดสร้างคำสั่งได้โดยไม่ต้องแก้โค้ด | เปิด stop แล้วตรวจว่าไม่มี intent ใหม่ |

การอ่านข้อมูลที่ลองใหม่ได้อาจใช้ backoff ตามขอบเขต เช่นรอ 1, 2, 4 วินาที แล้วหยุดพร้อมบันทึกเหตุผล นี่เป็นตัวอย่างนโยบาย retry ไม่ใช่ค่า rate limit ของ Webull ส่วนการส่งคำสั่งต้องรู้ semantics ของ ID และการตรวจผลก่อนลองใหม่ จึงไม่ควรใช้ retry decorator เดียวครอบทุก API call

Journal ใน Notebook ใช้ JSON เพื่อการเรียน ยังไม่ได้มี transaction, lock, การป้องกันสอง process ส่งพร้อมกัน หรือการรับประกันข้อมูลลงดิสก์เมื่อไฟดับ ระบบจริงต้องมี storage/coordination ที่รองรับความต้องการเหล่านี้ การซ้อม recovery จึงต้องตรวจทั้งตรรกะและคุณสมบัติของที่เก็บข้อมูลที่เลือก

บทนี้ไม่ได้สร้างเซิร์ฟเวอร์ เชื่อมบัญชี หรือลงโปรแกรมตามตัวอย่าง cloud ของหนังสือ สิ่งที่ส่งมอบคือข้อกำหนดและงานทดลองออฟไลน์ที่ใช้ทบทวนความพร้อมได้

## แบบฝึกหัดปิดหลักสูตร: พิสูจน์ว่าหยุดถูกจุด {#exercise}

แก้รายการทดสอบสามกรณี แล้วเก็บทั้ง input, เหตุผลที่ระบบให้ และผลที่คาดไว้:

1. หลัง recovery ถือ 10 หุ้น มี pending buy 9 หุ้น จะซื้อเพิ่ม 3 หุ้น แม้มูลค่าคำสั่งเพียง 300 USD ควรผ่านหรือไม่?
2. เกิด intent ที่ยังไม่มี ACK แม้จำนวนหุ้นในเครื่องตรง snapshot ควรปลด pause หรือไม่?
3. มีผลขาดทุนรายวันเท่ากับ −20 USD พอดี ควรทำอย่างไรตามกติกาบทนี้?

**แนวเฉลย:** กรณีแรกไม่ผ่าน `POSITION_LIMIT` เพราะ `10 + 9 + 3 = 22 > 20` กรณีที่สองไม่ผ่าน `STATE_UNCERTAIN` เพราะคำสั่งอาจได้รับแล้วแต่ยังไม่แสดงผล กรณีที่สามไม่ผ่าน `LOSS_LIMIT` เพราะเงื่อนไขใช้ `<=` จึงรวมจุดขอบเขตด้วย

สำหรับการทบทวนทั้งหลักสูตร ให้รัน Notebook ทุกบทจาก kernel ใหม่ อธิบายสัญญาณโดยไม่มองผลอนาคต ตรวจต้นทุนและบัญชีได้ แล้วใช้เหตุการณ์ผิดปกติในบทนี้ทดสอบส่วนดำเนินการ หากแต่ละชั้นอธิบายผลได้ชัดเจน คุณจะมีฐานสำหรับพัฒนาระบบต่อโดยรู้ว่าส่วนใดผ่านการตรวจและส่วนใดยังต้องทดลอง
